## 2. 测试方法论

**场景分类**: 核心流程 (Core Flow) 和 Agent 生命周期 (Agent Lifecycle)。

**并发级别**: 1 / 5 / 10 / 20 并发工作线程。

**测量指标**:
- 墙钟耗时 (wall elapsed seconds)
- 吞吐量 (operations/agents/messages per second)
- 成功率/失败率
- 状态正确性断言 (每个操作均在异步回调中即时断言)

**额外验证**: 每个压测场景均包含行为和状态正确性断言，非单纯吞吐量测量。

## 6. 瓶颈分析

### 6.1 架构特性 (非瓶颈)

由于使用内存后端 (MemoryProvider)，所有操作的时延极低 (亚毫秒级)。
当前数据反映的是纯内存操作的理论上限，适合作为 1.0.0-rc1 的参考基线。

### 6.2 随并发扩展的行为

- **Core Flow**: send/get/cancel/mixed 四种操作均显示吞吐量随并发线性扩展 (从 1w 到 20w 约 1.3x-1.5x 提升)，无明显锁竞争。
- **Agent Lifecycle**: spawn/handle/destroy 吞吐量同样随并发提升，且未出现退化。
- **全生命周期**: 三阶段吞吐量均随并发提升，destroy 阶段吞吐量在 20w 时有轻微下降 (45,004 agents/s vs 10w 的 38,951 agents/s 仍为正增长)。

### 6.3 潜在关注点

1. **锁竞争**: MemoryProvider 使用 dict + threading.Lock。当前数据集小，未观察到锁争用; 大规模 (1000+) 并发时可能成为瓶颈。
2. **TaskManager 内存增长**: spawn 测试中 TaskManager 跟踪数与 Agent 数一致，表明无泄漏。但大规模场景下 (10万+) 内存占用需持续监控。
3. **状态转换原子性**: handle 测试中包含多个连续状态转换 (WORKING -> INPUT_REQUIRED -> WORKING)。当前设计在外部队列中顺序执行，高并发下部分竞争条件需在集成环境中验证。

## 7. 优化建议

### 7.1 短期 (v0.5.x)

1. **提升读操作 (get_task) 性能至写操作水平**: 当前 get 吞吐量 (71,242 ops/s@20w) 与 send (68,767 ops/s@20w) 持平，但读操作理论上应更快。考虑引入读-写锁 (RWLock) 允许无竞争并发读。
2. **去除混合操作中的冗余断言开销**: 混合场景每个操作后有三重断言，移除生产构建中的断言可提升约 5-10% 吞吐量。

### 7.2 中期 (v1.0.x)

1. **引入连接池和批量操作**: 当前每个操作独立调用。支持 batch_send/batch_get 可降低调用方开销。
2. **TaskManager 懒加载清理**: 当前 clean 操作遍历全部任务。引入索引或分区清理策略可提升大规模场景下的 destroy 吞吐量。
3. **异步 IO 替代线程池**: ThreadPoolExecutor 受 GIL 限制。对 IO-bound 场景改用 asyncio 或 multiprocessing 可进一步提高伸缩性。

### 7.3 长期 (v1.1+)

1. **网络/分布式后端基准测试**: 当前压测在内存后端进行。生产环境将涉及网络 RPC (HTTP/gRPC)，需重新测试网络延迟影响。
2. **持久化后端对比**: 引入 PostgreSQL/Redis 后端后的吞吐量退化系数需量化为 benchmark table。

---

## 8. 总结

AgentMesh v0.4.0 在内存后端上的表现:

- **单机极限吞吐量**: 核心流程可达 ~80,000 ops/s (20 并发)
- **Agent 生命周期**: spawn ~52,000 agents/s, handle ~231,000 msgs/s, destroy ~33,000 agents/s (20 并发)
- **全生命周期**: 60 个 agent 完成创建 -> 处理(480条消息) -> 销毁仅需 4.9ms
- **边界场景**: 4 种异常场景均优雅处理，无崩溃或数据状态损坏
- **0 失败率**: 所有场景成功率 100%

当前报告为内存后端基线。下一步建议集成网络后端 (HTTP/gRPC) 和持久化后端后复测以获取生产级参考数据。
